# ADR-0028: Skill packages carry their own eval trace

**Status:** Accepted
**Date:** 2026-08-22
**Owner:** CoDev maintainers
**Related design:** [../features/skill-eval-ergonomics/design.md](../features/skill-eval-ergonomics/design.md)

## Context

Until now, `codev eval benchmark run <skill>` wrote its full report only to
the caller-chosen `--output` directory -- an arbitrary, throwaway location the
skill itself never referenced. A skill installed under `.agents/skills/<name>/`
was just `SKILL.md` plus supporting files; nothing about the skill's own
directory said whether it had ever been benchmarked, or what the result was.
A developer opening a skill folder had no way to tell "does this actually
help" without separately locating whatever `--output` directory a past run
happened to use, if it still existed at all.

NVIDIA SkillEvaluator's own Recommended Artifact Set for a released skill
package (https://docs.nvidia.com/skills/agent-skill-trust-pipeline) treats
this as a first-class part of the package, not an external byproduct:
alongside `SKILL.md`, it expects `BENCHMARK.md` (Tier 3 per-dimension scores
and verdict) and an evaluation dataset at one of a few conventional paths,
the most common being `evals/evals.json`. CoDev's own `codev eval nvidia
tier3 evaluate --autopilot` already independently produces exactly this
shape today (`.agents/skills/audit-google-python-style/evals/evals.json`,
a side effect of the external tool, not something CoDev wrote deliberately) --
concrete, unplanned confirmation that this is the natural location, not an
arbitrary choice invented for this ADR.

## Decision

`codev eval benchmark run <skill>` packages its report into the skill's own
directory as a durable eval trace, mirroring NVIDIA's artifact set:

- `.agents/skills/<skill>/evals/benchmark.json` -- the same report shape
  already written to `--output/benchmark.json`, plus a `generated_at`
  timestamp. Machine-readable, the source of truth for the trace.
- `.agents/skills/<skill>/evals/BENCHMARK.md` -- a Markdown rendering of the
  same data (per-category with/baseline/delta table), for a developer
  browsing the skill folder directly, matching NVIDIA's literal `BENCHMARK.md`
  filename convention.
- `codev eval show <skill>` reads the packaged trace back and renders it as
  text, without the caller needing to know or retain any `--output` directory
  from a past run.

Packaging happens automatically, by default, only for an *unrestricted* run
(no `--category` filter) -- a category-restricted run is already documented
as a cheap partial trial (see `design-skill-eval`'s
`eval-design-checklist.md`), and packaging it would silently make the trace
claim coverage the run didn't have. `--no-package` opts out entirely (e.g. a
scratch or CI dry run against a target the caller doesn't want written to).
If the named skill isn't installed under `.agents/skills/` in the target
repository, packaging is skipped with no error -- the caller's own `--output`
directory already durably holds the full report regardless, and a missing
skill directory is not a reason to fail an otherwise-successful benchmark
run.

CoDev adopts only the eval-trace half of NVIDIA's artifact set. `skill-card.md`
(ownership/license/risk metadata) and `skill.oms.sig` (a signing step) solve
problems CoDev does not yet have -- there is no catalog, no publication
step, and no cross-organization trust boundary for an installed skill to be
signed against. Adopting those now would be speculative infrastructure for a
problem this project doesn't face; see Revisit when.

## Alternatives considered

- **Keep the trace only in the caller's `--output` directory:** rejected --
  this is the status quo being fixed. It gives no way to answer "has this
  skill been benchmarked, and how did it do" from the skill's own directory.
- **Always package, even for a `--category`-restricted run:** rejected. A
  partial run's trace would silently overwrite (or be indistinguishable from)
  a previous full run's trace, misrepresenting the skill's actual measured
  coverage.
- **Adopt the full NVIDIA Recommended Artifact Set now (skill-card.md,
  signing):** rejected for this decision. CoDev has no catalog or
  cross-organization publication step for those to attach to yet; see
  Revisit when.
- **A separate `codev eval package <skill>` command, run explicitly after
  `benchmark run`:** rejected as an unnecessary extra step for the common
  case -- packaging the report is what makes the trace exist "if it exists"
  from `codev eval show`'s perspective, and a benchmark run already produces
  everything packaging needs.

## Consequences

- A skill's directory now optionally contains an `evals/` subdirectory that
  isn't hand-authored -- it's fully regenerated by `codev eval benchmark run`
  and should be treated as a build artifact, not edited by hand.
- Every full benchmark run overwrites the previous trace; there is no
  history of past traces beyond whatever the caller's own `--output`
  directories (or Git history, once committed) retain.
- A skill can be reviewed, distributed, or version-controlled with its own
  evidence of measured effect traveling alongside it, rather than requiring a
  separately preserved `--output` directory.

## Revisit when

CoDev grows a real skill catalog, a publication/distribution step, or a
cross-organization trust boundary an installed skill needs to be verified
against -- at that point, revisit whether `skill-card.md` and an OMS-style
signature belong in this same artifact set, rather than inventing a
CoDev-specific mechanism for the same problem NVIDIA has already solved.
